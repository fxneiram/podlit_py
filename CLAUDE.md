# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

This is a personal language-learning tool, not a general-purpose media generator. The owner
speaks Spanish and is learning English; the point is to take any content they choose — a book
summary, a news article, whatever they're in the mood to read about — and turn it into audio
(and video) that alternates fragment by fragment between the two languages, so listening to it
repeatedly reinforces the target language against a native-language anchor. Any feature you add
should keep that alternating-fragment listening experience intact, not just "generate audio in a
language."

## What this project does

PodLitPy turns a bilingual (EN/ES) text script — typically generated by pasting a book/topic
summary prompt into ChatGPT (see the prompt template in [README.md](README.md)) — into narrated
audio (WAV) and video (MP4) files, using Coqui TTS (XTTS v2) for speech synthesis. It's a
single-user desktop Tkinter app, not a service.

## Commands

Always work inside the `tts` conda environment (`.windsurf/rules/env.md` enforces this) — the
app imports `TTS.api` and `torch` directly and will fail outside it.

```bash
make install         # install-ffmpeg + create-env (conda env "tts", py3.9) + install-deps
make run              # conda activate tts && python app.py
make clean            # remove __pycache__ and .pyc files
```

There is no test suite in the repo yet. The dev-workflow skill (see below) introduces
`tests/unit/` and `tests/integration/` with pytest as work happens — run a single test the
normal pytest way once tests exist: `pytest tests/unit/test_foo.py::test_bar`.

`pyproject.toml` configures `ruff` (lint + format), `mypy`, and pytest; `ruff check .` /
`ruff format --check .` / `mypy .` / `pytest` also run in CI (`.github/workflows/ci.yml`) on
every PR into `develop` — `ruff`/`mypy` are advisory for now since the legacy code predates
these standards (see `coding-standards.md` below), `pytest` is blocking.

Dependency versions are pinned deliberately in `requirements.txt` (`torch`/`torchaudio` CPU
wheels, `TTS==0.22.0`, `numpy==1.22.0` — `TTS==0.22.0` declares this exact numpy version as its
own dependency; anything else fails `pip`'s resolver outright). Don't bump these without reason.

## Architecture

**Entry point**: `app.py` builds one `AudioVideoGenerator` (the generation engine) and one
`WindowTaskQueueManager` (the Tkinter UI), then runs the Tk mainloop.

**The task queue's real shape is plain dicts, not the `models/` classes.** A "task" as it
flows through `WindowTaskQueueManager`/`TreeviewTaskQueue` is a raw Python dict shaped like
`{1: {"text": "...", "language": "en"}, 2: {...}, ...}` — the ordinal keys and the two-language
alternation come directly from the ChatGPT prompt template. `models/task.py` (`Task`) and
`models/row.py` (`Row`) exist to *validate/parse* that shape (`Task.validate_input` via
`ast.literal_eval` for pasted text, `Task.build_from_string` via `json.loads` for files) — they
are not the object actually stored in or iterated over by the queue. Don't assume `Task`/`Row`
instances flow through `AudioVideoGenerator`; they don't today.

**Generation pipeline** (`audio_video_generator.py: AudioVideoGenerator.generate_files`):
for each ordered dict entry — TTS synthesizes to a temp WAV (`TTS.tts_to_file`, device is
`cuda` if `torch.cuda.is_available()` else `cpu`, chosen once at startup) → `AudioManager.add_silence`
pads it to a full-frame boundary at the configured FPS → `VideoManager.generate_fragment` renders
a static text-on-background image, stretches it to the audio's duration via `cv2.VideoWriter`,
then muxes in the audio with an `ffmpeg` subprocess call. Once every row has a fragment,
`AudioManager.combine_audio_fragments` / `VideoManager.combine_video_fragments_ffmpeg` concatenate
all fragments into the final output files, named from the sanitized first row's text
(`FileManager.get_final_file_names`).

**Queue-level mixing**: when "Mix Queue" is checked, after all queued tasks finish,
`AudioVideoGenerator.combine_queue` concatenates each task's *already-generated* output
audio/video files into one combined file — this is a second, separate concatenation pass on top
of the per-task one above.

**Threading model**: each task in the queue runs in its own background `threading.Thread`
(`WindowTaskQueueManager.process_task_in_thread`), polled from a `root.after(100, ...)` loop so
the Tkinter mainloop never blocks; a configurable delay (`task_delay`, minutes → ms) is inserted
between tasks via `root.after` as well.

**Persistence**: queue save/load (`btn_action_save_queue`/`btn_action_load_queue`) uses `pickle`
on `.que` files against the raw dict list — a different serialization path than the JSON used by
`Task.build_from_string` for "Add From File". Keep this in mind if you touch either path; they
are not currently unified.

**`fh/` package** — thin, library-specific managers called directly by `AudioVideoGenerator`
(no abstraction layer today): `hfiles.FileManager` (temp/output paths, filename sanitization,
random path generation), `haudio.AudioManager` (pydub silence padding/concatenation),
`hvideo.VideoManager` (PIL/cv2 frame rendering + `ffmpeg` subprocess concatenation).

**`pkg/config.py`** holds all shared constants (paths, colors, sizes, FPS) — the single place
to look for or add tunables rather than hardcoding in `fh/`/`tk/`.

## Development process

This repo has a required process encoded as a Claude Code skill at
`.claude/skills/dev-workflow/SKILL.md`: issue/instruction intake → branch → spec-first (SDD,
stop for confirmation) → TDD (unit tests before code) → implementation in small commits →
integration tests → self-review (`/code-review`) → fix findings → PR (stop for confirmation) →
CI verification. It also mandates migrating the codebase toward a hexagonal architecture
(ports & adapters) — the target package layout and incremental migration strategy are in
`.claude/skills/dev-workflow/references/hexagonal-architecture.md`. Read that before deciding
where new code belongs; the flat layout described above is the *current*, pre-migration state.

Coding standards (100% English code/comments/commits, comments only when necessary, PEP 8 +
type hints, typed domain exceptions instead of bare `except Exception`, `subprocess.run` with
arg lists instead of `os.system`, `logging` instead of `print`, `ruff`/`mypy` for lint/format/
types) are in `.claude/skills/dev-workflow/references/coding-standards.md`. The current codebase
predates this standard (Spanish comments, bare excepts, `os.system` calls in `fh/hvideo.py`,
stray `print`s) — fix a module's instances as you touch it, don't do a standalone cleanup pass.
